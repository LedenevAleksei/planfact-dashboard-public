# Ключевые решения (ADR-лайт)

Записи о принятых решениях и их обоснованиях. Новые — снизу.

## 1. API ПланФакта — только чтение
**Решение:** через API ничего не создаём/меняем/удаляем. Только чтение и рекомендации.
**Почему:** ведётся реальный управленческий учёт компании; ошибочная запись исказит отчётность. Правки пользователь делает вручную в интерфейсе, осознанно.

## 2. Ключ только из .env, у каждого свой
**Решение:** `PLANFACT_API_KEY` хранится в `.env` (в `.gitignore`), в браузер/логи/чат не попадает. Новый сотрудник использует собственный ключ.
**Почему:** безопасность; изоляция доступов; папку можно передавать без секретов.

## 3. Разделение fetch/build
**Решение:** `fetch_data.py` (обращение к API) отделён от `build.py` (рендер HTML) через промежуточный `data/dashboard.json`.
**Почему:** можно отлаживать UI на закэшированных данных без нагрузки на API; в Фазе 2 backend переиспользует `fetch_data.py` для кнопки «Обновить» и cron.

## 4. Ключ на сервере (Фаза 2)
**Решение:** дашборд ходит в API только через backend; клиентский JS ключ не видит.
**Почему:** иначе ключ утечёт в браузер. Это определяет архитектуру веб-версии (Flask + серверный `/refresh`).

## 5. Определение дебиторки/кредиторки
**Решение:** дебиторка = Income с `isCommitted=false` и `isCalculationCommitted=true`; кредиторка = аналогично по Outcome. Контрагент-заглушка «Планир(у)мая себестоимость» исключается.
**Почему:** это реальные обязательства (начислено, но не оплачено), а не планы. «Плановая себестоимость» — прогноз затрат заказов, не долг поставщику.

## 6. Недельные корзины в реестрах
**Решение:** `Просрочено` │ `Тек. неделя` │ +6 недель │ `Позже`; неделя = ожидаемая дата оплаты (`operationDate`).
**Почему:** так CEO видит ближайшие обязательства и просрочку. Горизонт (6) вынесен в `HORIZON`.

## 7. Блок «Продажи»: «получено» привязано к месяцу продажи
**Решение:** и «Продано по договорам», и «Получено фактически» ключуются по **дате начисления** (месяцу продажи проекта). «Получено» = оплаченная часть проектов, проданных в этом месяце (предоплаты/доплаты), независимо от даты платежа. Поэтому «получено ≤ продано» всегда, а разница = дебиторка по продажам месяца.
**Почему:** нужно видеть собираемость по когорте месяца продажи, а не мешать притоки за старые заказы. Учёт денег по датам платежей ведётся отдельно в ДДС (раздел 4).

## 8. P&L и «маржинальность» (открыто)
**Статус:** пока P&L показывает все расходы. Для «маржинального» нужна разметка статей на прямые/переменные vs постоянные — ждём принцип от пользователя.

## 9. Одобрение платежей и реестры — только на клиенте
**Решение:** режим одобрения, реестры платежей и «висящие» одобренные суммы реализованы полностью на клиенте (браузерный JS + `localStorage`, ключ `planfact_registers`). API ПланФакта не вызывается на запись. Реестр — локальный артефакт (для печати/банка), проводит платёж человек вручную в ПланФакте.
**Почему:** правило №1 — API только для чтения. Дашборд не может и не должен создавать/менять операции. Чтобы одобренные суммы не «терялись» при пересборке данных и не задваивались с фактом, они привязаны к `operationId` и держатся, пока платёж не исчезнет из кредиторки (= проведён в ПланФакте) — тогда снимаются автоматически.
**Ограничение:** localStorage привязан к браузеру.

## 11. Хостинг: бэкенд на Railway, Cloudflare Access впереди (не Netlify/Pages)
**Решение:** дашборд ПланФакта остаётся Flask-бэкендом на Railway (нужен долгоживущий Python-процесс: ключ, `/refresh`, cron, прокси в Supabase). Cloudflare используется как фронт: DNS-домен + **Cloudflare Access** для входа. Приложение авторизует по ЛИБО валидному Access-JWT, ЛИБО Basic-Auth.
**Почему:** Netlify/Cloudflare **Pages** — это хостинг статики (+ serverless JS/TS); наш Python-бэкенд туда не ложится без полной переписки выгрузки на TypeScript-Worker. Вариант A (Cloudflare перед Railway) переиспользует весь готовый код и даёт вход через уже существующую у пользователя авторизацию Cloudflare Access. Basic-Auth оставлен как второй слой, потому что Cloudflare Access не прикрывает прямой `*.up.railway.app` (Access защищает только трафик через Cloudflare) — иначе был бы обход.
**Личный проект `money-dashboard-aleksei` на Netlify — не трогаем** (это другой, личный дашборд, не ПланФакт; по указанию пользователя оставлен как есть).

## 10. Реестры платежей — в Supabase через backend (Фаза 2)
**Решение:** реестры хранятся в Supabase (таблица `public.pf_payment_registers`, проект servicebot). Браузер ходит в наш Flask `/api/registers` (за Basic-Auth), а сервер — в Supabase **сервисным ключом** (`SUPABASE_SERVICE_KEY` из env). Клиент держит кэш реестров в памяти; при `file://`/недоступности API откатывается на localStorage (совместимость с Фазой 1).
**Почему:** реестры должны быть общими для устройств/браузеров и переживать смену устройства (снимает ограничение из #9). Ключи Supabase (anon и service) в браузер не отдаём — та же логика, что с ключом ПланФакта: секреты только на сервере. RLS на таблице включён без политик → доступ только сервисным ключом (как `billing_events` в servicebot). Правило №1 не нарушается: пишем в СВОЮ базу, API ПланФакта остаётся read-only.
**Обновление:** по той же схеме в `pf_settings` (key-value) + `/api/settings` вынесены **все клиентские настройки** — ручной остаток банка, план продаж, валюта, порядок меню, ширина колонки. Раньше жили в localStorage у каждого свои; по требованию пользователя «сделать всё общее» теперь видны всем под одним логином. localStorage остаётся только как offline-fallback (Фаза 1 / недоступность сервера). Разовая миграция плана из localStorage на сервер при первой загрузке.
